# 列表预加载与多页同时加载（fork 自维护）

上游未合并（PR #153 关闭），本 fork 单独维护。两个开关都在「功能开关」里，默认关闭；关闭时行为与上游完全一致。

## 开关与行为

| 开关 | 设置项 | 开启后 |
|---|---|---|
| 列表预加载 | `enableListPreload` | 13 个分页列表离底 8 屏就请求下一页（`useListPreload`），并隐藏竖向滚动条；不加大 `drawDistance`（真机实测 1500px 让快速滑动掉帧从约 3% 升到 10–17%） |
| 多页同时加载 | `enableParallelPaging` | 个人主页回答、提问、文章、想法按 offset 一次请求 3 页（`fetchOffsetPages`）；未开列表预加载时，登录态推荐流用请求接力队列提前请求下一页（`PageQueue`，深度 1） |

设置版本 v22 加预加载、v23 加多页加载。上游以后升级设置版本时，需要把这两条迁移重新编号到上游之后。

## 与上游分页的衔接

上游推荐流、日报、个人主页用 `useEndReachedPagination`：触底时只发一次请求，忙时排队，加载后列表没变长才最多补请求 3 次。预加载在它之上只改两处：

1. **触发距离**：`endReachedThreshold` 与 FlashList 的 `onEndReachedThreshold` 都改用 `useListPreload` 给出的值。
2. **补请求**：FlashList 只在列表“进入”底部区域时调用一次 `onEndReached`。8 屏的区域能装下好几页，新页到达时阅读位置往往还在区域内，不会再触发，上游的补请求又只在列表没变长时才发，所以分页会停住，直到用户滑到真正的底部。`useLoadMoreNearEnd` 在预加载开启时，每次加载结束后只要仍在区域内就调用上游的 `handleEndReached`，同一滚动位置最多补 3 次。

其余 10 个普通列表没有接入上游的 hook，只改了触发距离。

## 推荐流的阅读反馈与请求接力

- **已读上报**：上游在请求下一页时上报上一页的回答（`lastread/touch`）。预加载提前好几屏请求，这样会把没看到的内容报成已读，所以开启预加载时 `useFeedPageReadTouch(…, reportOnPass)` 不在请求时上报，改由 `useFeedReadTouchOnPass` 处理：后一页的卡片出现在屏幕上（露出一半且停留 800ms，折叠行按其第一张卡片算）时，上报它之前各页的整批回答。
- **请求接力**：只在开了「多页同时加载」、没开「列表预加载」时运行（`shouldRelayRecommendations`）。两者都开时接力没有收益（见下方实测），还会在会话结束时多请求一页，所以不启用。推荐游标带 `session_token`，可能参与服务端的推荐会话状态，所以队列只提前请求上一页 `paging.next` 给出的那一页，不推测、不乱序。服务端收到的请求和关闭开关时相同、顺序相同，只是更早发出。只有当前显示的列表维持队列；关闭开关、切换账号、卸载时清空队列。下拉刷新不清空队列：刷新成功前旧页面保留，刷新失败时继续使用已经请求到的下一页，避免同一游标请求两次；刷新成功后会排入新的下一页，旧会话的请求随之中止。

## 实测（2026-11-18）

**推荐流（Android 13 模拟器，登录态，release 包）**：用 adb 匀速滑动模拟阅读，开关交替各跑 2 轮。"触底等待"是读者停在列表最底部、还有下一页没到的累计时长；单页请求约 1.1–1.2 秒。

| 设置 | 阅读速度 | 接力开：触底等待 | 接力关：触底等待 | 结论 |
|---|---|---|---|---|
| 关预加载 | 中速，45 秒 | 0 / 0 秒 | 8.6 / 7.1 秒 | 接力有效：下一页在读者到底前已取好 |
| 开预加载 | 中速（约 1 屏/秒），45 秒 | 0 / 0 秒 | 0 / 0 秒 | 8 屏缓冲已掩盖等待，接力无额外收益 |
| 开预加载 | 快速甩动，40 秒 | 23.5 / 20.0 秒 | 23.4 / 18.6 秒 | 两者相同：瓶颈是串行请求，每页约 1.2 秒 |

接力深度为 1，在上一页返回后才请求下一页，这时开了预加载的列表本身也正好在要下一页，所以两者叠加没有收益，现在开预加载时不再启用接力。只想解决中速阅读时的触底等待，单开「多页同时加载」（推荐流接力）就够了，而且比 8 屏预加载提前请求的页少。快速甩动时要提速，只能并发请求多页，但这需要推测游标，出于推荐会话的考虑已经放弃。

**个人主页 3 页并发（浏览器，登录态，与 App 相同的 `x-zse-96` 签名）**：33 个请求，其中 8 批是 3 页并发、5 批连续发出，全部返回 200，没有 40362、403 或验证码。3 页并发一批约 3 秒，和单页请求的中位耗时（约 3 秒）相当。样本量小，不能排除长时间重度使用时触发风控。

同一次测试发现接口偶尔返回 39 条的"双倍页"（offset 80、480），和下一页重叠 20 条。个人主页的列表跨页拼接时原本没有去重，关闭开关（即上游行为）也会出现重复卡片；现已改为按 id 去重（`flattenUniquePages`，已提给上游 PR #198）。

## 已知代价

- 每个推荐会话结束时（刷新成功、退出），最后一页已经提前请求、但没有展示。服务端可能把这页算作已下发。
- 列表的查询被取消时（例如刷新开始时取消正在翻的页），被取消的那页会再请求一次。这和上游一样：被中止的请求可能已经到达服务端。
- 个人主页 3 页并发更容易触发知乎风控（40362）。

## 回归

`listPreload`、`listPreloadPagination`（按 FlashList 的边沿触发模拟阅读：只调阈值会在第 2 页后停住）、`pageQueue`、`usePageQueue`、`parallelPaging`（含接力只在预加载关闭时运行）、`feedReadTouchPass`、`feedPageReadTouch`（reporting on pass）、`userProfileScreen`（多页同时加载、双倍页不重复）、`userProfile`（`flattenUniquePages`）、`featureSettings`、`settings-renderer-migration`。真机需检查开启后快速滑动是否转圈、掉帧（`dumpsys gfxinfo`），以及有没有重复的分页请求。
